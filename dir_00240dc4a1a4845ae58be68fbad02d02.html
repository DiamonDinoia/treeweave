Detailed Description

Thin wrappers that let you fit and evaluate a canopy piecewise-Chebyshev approximant from Python, Julia, MATLAB/Octave, or Fortran, passing a function handle written in the host language into the fit and getting C++ fit failures back as native exceptions.

All sit on the same C ABI (libcanopy_c, see ../include/canopy.h) and reuse its pre-instantiated shapes — they do not re-instantiate the C++ templates. The mechanism is identical in spirit across languages: the wrapper hands the C fit a C function pointer (a trampoline) plus an opaque context pointer carrying the host callable; the trampoline re-enters the host language once per Chebyshev sample.

In the Python, Julia, and MATLAB wrappers the fitted object is simply called — with a point or a batch — and fit infers dim and out_dim (the latter by probing your function once at the box midpoint), so the common call is just fit(f, a, b, tol). Two optional flags, sorted (1-D ascending fast path) and transposed (struct-of-arrays out_dim × N output), select the alternate batch modes. The Fortran binding is deliberately faithful instead: explicit named procedures with explicit input_dim / output_dim, no call operator.

Supported values
input dim 1, 2, 3
output dim 1, 2, 3 (a 1-D vector-valued fit is dim=1, out_dim>1)
dtype f64 (double), f32 (float)

Domain note (all languages): the lower corner a is inclusive but the upper corner b is exclusive — evaluating exactly at b returns NaN (the out-of-domain sentinel). Sample [a, b).

Reverse-exception safety (all languages): if your host callback raises during the fit, the trampoline catches it, writes NaN, short-circuits the remaining samples (it never re-enters the host language again), lets the C fit unwind cleanly, and then re-raises the original exception. A throwing callback never crashes the interpreter / corrupts the C++ stack.

Python (nanobind)

pip install ./bindings/python # scikit-build-core fetches nanobind, builds the extension
pytest bindings/python/tests
import numpy as np, canopy
f = canopy.fit(lambda x: np.exp(0.5*x[0]) + np.sin(3*x[0]), 0.0, 1.0, tol=1e-8)
f(0.5) # scalar
f(np.linspace(0, 1, 100, endpoint=False)) # vectorized -> (100,)
f(np.linspace(0, 1, 100, endpoint=False), sorted=True) # 1-D ascending fast path
f.memory_usage, f.dim, f.out_dim, f.dtype
# 2D -> 3D vector-valued; out_dim is inferred by probing the callable
g = canopy.fit(lambda x: np.array([np.exp(0.3*x[0]) + np.sin(2*x[1]),
np.cos(x[0]*x[1]) + 2.0,
x[0]**2 + x[1] + 1.0]),
[0.2, 0.2], [1.5, 1.5], tol=1e-7)
X = np.random.uniform([0.2, 0.2], [1.5, 1.5], size=(64, 2))
g(X) # -> (64, 3)
g(X, transposed=True) # -> (3, 64)

Julia

# No env var needed: the package walks up to find a sibling build*/ tree.
julia --project=bindings/julia/Canopy -e 'using Pkg; Pkg.test()'

The library is located in order: LIBCANOPY_C (explicit path) → deps/deps.jl (written by Pkg.build("Canopy")) → the loader search path → a sibling CMake build*/libcanopy_c.<ext>. So an in-repo Pkg.test() works once the project has been built; set LIBCANOPY_C=/path/to/libcanopy_c.so to override.

using Canopy
b = fit(x -> exp(0.5x) + sin(3x), 0.0, 1.0, 1e-8) # dim==1: f(scalar)
b(0.5) # point
b(collect(range(0, 1, length=100))) # dim==1 batch -> length-100 vector
# 2D -> 3D: f(coords...) returns an indexable of length out_dim (inferred)
g = fit((x, y) -> (exp(0.3x) + sin(2y), cos(x*y) + 2, x^2 + y + 1),
[0.2, 0.2], [1.5, 1.5], 1e-7)
g([0.5, 0.7]) # point -> length-3 Vector
g(rand(64, 2)) # batch -> 64×3
g(rand(64, 2); transposed=true) # -> 3×64

A NULL fit raises error(canopy_last_error()); a raising closure is re-thrown after the fit. See julia/Canopy/README.md.

MATLAB / Octave (MEX)

mwrap is the real generator: canopy.mw is the source of truth, and the generated gateway (canopy_mex_gen.cpp) + bz_*.m stubs are committed. A plain build compiles the committed gateway — no mwrap or network needed:

# MATLAB (no license needed; -static-libstdc++ keeps the .mexa64 independent of
# MATLAB's bundled libstdc++).
make -C bindings/matlab MATLAB_ROOT=/usr/local/MATLAB/R2025b
matlab -batch "run('bindings/matlab/test_canopy.m')"
# GNU Octave (build from source with mkoctfile; not shipped prebuilt).
make -C bindings/matlab octave CANOPY_BUILD="$PWD/build"
octave --no-gui --eval "addpath('bindings/matlab'); test_canopy"

The same committed gateway serves both: Octave can pass a function_handle into a MEX and feval it, so the trampoline needs no Octave-specific path.

To change the binding, edit canopy.mw and regenerate with make -C bindings/matlab mwrap_gen (or the CMake regenerate-matlab target). The CMake glue regenerates automatically when canopy.mw is newer than the committed gateway, discovering mwrap on PATH or cloning + building the official mwrap (plain make — flex/bison are needed only to modify mwrap's grammar).

f = @(x) exp(0.5*x(1)) + sin(3*x(1));
obj = canopy(f, 0, 1, 1e-8); % dim & out_dim inferred
obj(linspace(0, 1, 100)') % subsref syntax; or obj.eval(...)
obj(linspace(0, 1, 100)', 'sorted', true) % 1-D ascending fast path
g = canopy(@(x) [exp(0.3*x(1))+sin(2*x(2)), cos(x(1)*x(2))+2, x(1)^2+x(2)+1], ...
[0.2 0.2], [1.5 1.5], 1e-7); % out_dim inferred (=3); degree auto per CPU
g(rand(100,2)*1.3 + 0.2) % -> 100x3
g(rand(100,2)*1.3 + 0.2, 'transposed', true) % -> 3x100

A C++ fit failure raises canopy:fit; a callback error raises canopy:callback. See matlab/README.md.

libstdc++ / GLIBCXX note (fallback only). The canonical Makefile (and the CMake glue) link the C++ runtime statically (-static-libstdc++ -static-libgcc), so the .mexa64 does not depend on MATLAB's bundled libstdc++. Only if you build the mex some other way and MATLAB reports version GLIBCXX_3.4.xx not found do you need a workaround — e.g. launch MATLAB with LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libstdc++.so.6.

Fortran (iso_c_binding)

A faithful, thin Fortran 2008 binding: the module canopy binds every C symbol by name. Unlike the other wrappers it has no call operator and no inference — you pass input_dim / output_dim explicitly and write the target as a bind(C) callback, exactly as a C consumer would.

cmake -S . -B build -DCANOPY_BUILD_FORTRAN=ON
cmake --build build --target canopy_fortran_test canopy_fortran_example
ctest --test-dir build -R fortran_canopy --output-on-failure
use, intrinsic :: iso_c_binding
use canopy
type(c_ptr) :: h
real(c_double) :: a(1) = [0.0_c_double], b(1) = [1.0_c_double], x(1), y(1)
h = canopy_fit(c_funloc(kernel), 1_c_int, 1_c_int, a, b, 1.0e-10_c_double, &
c_null_ptr, c_null_ptr) ! kernel: bind(C) void(x, y, context)
x(1) = 0.5_c_double
call canopy_eval(h, x, y)
h = canopy_free(h)

State that a C++ lambda would capture goes through the context pointer (c_loc of a bind(C) type, recovered with c_f_pointer). See fortran/README.md for the full iso_c_binding mapping and the callback/context pattern.

Building via the top-level CMake

The wrappers are also wired into CTest, each behind an option (all default OFF):

cmake -B build -DCANOPY_BUILD_PYTHON=ON -DCANOPY_BUILD_JULIA=ON \
-DCANOPY_BUILD_MATLAB=ON -DCANOPY_BUILD_FORTRAN=ON
cmake --build build
ctest --test-dir build -R "python_canopy|julia_canopy|matlab_canopy|fortran_canopy"

Missing toolchains are detected and skipped with a STATUS message rather than failing configuration. (The Python CTest additionally needs numpy + pytest in the interpreter CMake selected; the Julia CTest passes LIBCANOPY_C pointing at the freshly-built shared library.)

Cross-language parity

parity/run_parity.sh fits the same 2-D → 3-D kernel in C (the reference), Python, and Julia, evaluates a fixed point set, and checks that every language agrees with the C result. See that directory for details.
