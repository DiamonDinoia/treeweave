Canopy

An adaptive fast function approximator based on tree search. canopy turns a CPU-intensive function into a cheap one (trading memory for time) by fitting it piecewise with low-order Chebyshev polynomials on an adaptive grid. It is conceptually similar to chebfun/chebeval but panelled, and typically reaches the same tolerance at lower polynomial order — which is faster on modern SIMD hardware.

Internally, canopy represents your function as a grid of binary / quad / oct / N-trees whose leaves carry the local Chebyshev expansion. Evaluation locates the leaf containing your point and runs a Horner-order polynomial.

Status

The core is a pure C++20 header-only template library. On top of it sits an optional C ABI (libcanopy_c) with runtime SIMD dispatch, plus Python, Julia, MATLAB/Octave, and Fortran wrappers — all under bindings/ and opt-in via CMake. The fit/eval code path is built on polyfit for the leaf polynomials and POET for compile-time dispatch.

Install

git clone https://github.com/flatironinstitute/canopy.git
cmake -S canopy -B canopy/build -DCMAKE_BUILD_TYPE=Release
cmake --build canopy/build -j 8

Header-only — no install step is needed beyond pointing your include path at canopy/include. See Building for the test build.

Quick start

A minimal 1D fit + scalar operator() (full file at examples/c++/simple1d.cpp):

#include <canopy/canopy.hpp>
#include <cmath>
int main() {
auto runge = [](double x) { return 1.0 / (1.0 + 25.0 * x * x); };
// Fit `runge` on [-1, 1] to 1e-10. Panel count falls out of the
// adaptive tree; the leaf degree defaults to 7 (best across the SIMD
// tuning campaign — see below; override with `fit<N>`).
auto fn = canopy::fit(runge, -1.0, 1.0, /*tol=*/1e-10);
return fn(0.3) != 0.0;
}

Multi-dimensional fits use std::array for both input and output:

auto bump = [](std::array<double, 2> x) -> std::array<double, 1> {
return {std::exp(-100.0 * (x[0] - 0.5) * (x[0] - 0.5)
- (x[1] - 0.5) * (x[1] - 0.5))};
};
auto fn = canopy::fit(bump,
std::array{0.0, 0.0}, std::array{1.0, 1.0},
/*tol=*/1e-8);

Override the leaf degree via the template parameter:

auto fn = canopy::fit<12>(f, a, b, /*tol=*/1e-10);

The C ABI follows the FINUFFT/FFTW idiom: precision lives in the library prefix, so canopy_fit is the double entry point and canopyf_fit its float twin (see canopy.h). It takes no degree argument — it auto-selects a register-optimal leaf degree for the detected CPU at runtime. On x86, building with -DCANOPY_C_MULTIARCH=ON enables multi-arch dispatch so the best ISA variant (SSE4.2, AVX2, AVX-512) is chosen automatically.

#include <canopy.h>
/* f(x)=exp(x) on [0,1]; context carries optional callback state (NULL here),
* opts is NULL for canopy_default_opts. */
double a = 0.0, b = 1.0, x = 0.5, y;
canopy_t fn = canopy_fit(kernel, /*input_dim=*/1, /*output_dim=*/1,
&a, &b, /*tol=*/1e-10, /*context=*/NULL, /*opts=*/NULL);
canopy_eval(fn, &x, &y); /* batch: canopy_batch / canopy_sorted / canopy_transposed */
canopy_free(fn);

tol is positional (no default) so every call site spells out its target accuracy — there is no "magic tol" overload.

canopy::options exposes the fit-time knobs (tol_kind, max_depth, max_memory_mib, allow_max_depth_leaves, min_uniform_depth). tol_kind is a canopy::TolKind enum:

Kind Meaning
TolKind::RelativeMax max-abs relative error on a sample grid
TolKind::AbsoluteMax max-abs absolute error
TolKind::RelativeL2 L2 relative error
TolKind::AbsoluteL2 L2 absolute error
TolKind::RelativeTail 1D only — coefficient tail estimate
TolKind::AbsoluteTail 1D only — coefficient tail estimate

Building

cmake -S . -B build -DCANOPY_BUILD_TESTS=ON
cmake --build build -j 8
ctest --test-dir build

Requirements: CMake ≥ 3.25, a C++20 compiler. polyfit / POET / Catch2 are pulled in via FetchContent (see cmake/canopy_deps.cmake).

Language bindings

A C ABI (libcanopy_c, header include/canopy.h) plus Python, Julia, MATLAB/Octave, and Fortran wrappers live under bindings/. Each lets you fit using a function handle written in the host language and surfaces C++ fit failures as native exceptions. In the Python, Julia, and MATLAB wrappers the fitted object is simply called — for a point or a batch — and fit infers dim and out_dim (the latter by probing your function once), so the common call is just fit(f, a, b, tol); sorted / transposed flags select the alternate batch modes. The Fortran binding is a faithful thin layer with explicit dimensions. They are opt-in CMake options (all default OFF):

cmake -S . -B build -DCANOPY_BUILD_PYTHON=ON -DCANOPY_BUILD_JULIA=ON \
-DCANOPY_BUILD_MATLAB=ON -DCANOPY_BUILD_FORTRAN=ON
ctest --test-dir build -R "python_canopy|julia_canopy|matlab_canopy|fortran_canopy"

Missing toolchains are skipped gracefully. See bindings/README.md for per-language build/usage, the cross-language parity check, and notes.

Including in your CMake project

canopy exposes two surfaces, with different consumption paths:

C ABI (libcanopy_c) — installable, find_package-able. Install canopy (cmake --install) and link the namespaced target. It is self-contained (only needs the installed canopy.h):

find_package(canopy REQUIRED)
target_link_libraries(your_target PRIVATE canopy::canopy_c) # shared
# or canopy::canopy_c_static for the static archive

C++ header-only template API — in-tree only. The canopy::canopy target carries the include/ tree and links polyfit/POET transitively, so just link it (no manual include dirs or polyfit/poet lines):

add_subdirectory(extern/canopy) # or FetchContent_Declare(canopy ...)
target_link_libraries(your_target PRIVATE canopy::canopy)

The C++ template API is not part of the installed find_package(canopy) package: it instantiates against polyfit/POET headers, which are FetchContent-only (not separately installable). So consume it via add_subdirectory / FetchContent (where those deps resolve), and use the installed package for the C ABI.

Driving the SIMD-quantize fast path

PolyTree::find_leaf_id has a SIMD-quantize + table-lookup fast path: one vcvttpd2qq (or scalar vcvttsd2si) per point plus one uint32_t load from a 2^(input_dim * D)-entry table, in place of recursive tree descent. The table is built automatically when input_dim * D <= 16 bits of leaf index and the BFS produced a single subtree with uniform refinement at depth D. The batch path's scatter loop then recomputes the leaf id in place of a materialised leaf_ids[] buffer.

For smooth functions, tol-based refinement usually stops early and the tree never reaches uniform depth — the fast path stays off. Two ways to drive it on deliberately: tighten tol until refinement is uniform, or set options::min_uniform_depth explicitly to force BFS to refine to a known floor before the tolerance test exits. Function::print_stats() reports Leaf table: live (N entries, K KiB) or Leaf table: descent-only. Tradeoff: table memory grows as 2^(input_dim * D) * 4 B (capped at ~256 KiB; past that the table is skipped) and build time is linear in 2^(input_dim * D) function evaluations.

Benchmarks

A small, stable set of batch-eval benchmarks (examples/c++/canopy_ci_bench) runs on every push to main and is tracked continuously at diamondinoia.github.io/canopy/dev/bench, which charts each series over time and flags regressions. The exhaustive exploratory history lives under bench/.

Thread safety

Once canopy::fit(...) returns, the resulting Function is immutable and its operator() is safe to call concurrently from multiple threads. Each call must write to a disjoint slice of res[]; per-call scratch is held in thread_local storage and the eval path never mutates shared state. Canopy does not parallelize internally — chunk your inputs and spawn threads yourself; this contract makes that pattern safe. Pinned by tests/test_threadsafe.cpp.

Limitations

  • Canopy can use a lot of memory on oscillatory or rapidly-varying functions. If your function is periodic, fit one period.
  • Canopy can't fit through a singularity — either shift the domain off the singular point or piecewise a small set of fits around it.
  • canopy dimensions are defined on the semi-open interval [x0, x1). Out-of-domain evaluations return NaN.
  • No bounds checking on user-provided inputs — it is up to the caller to sanitise.

Why the name?

It's a cute version of baobab, the tree of life. The baobab lives an extraordinarily long time, which is what this interpolator is meant to do — fit once, evaluate forever.
